# 多样化测试对话：case 设计与实测记录

这份文档说明 `eval/dialogues/cases.jsonl` 里 12 段对话**为什么这么设计**，以及
**实际跑出来是什么样、发现了什么问题**。

和 `eval/dataset/testset.jsonl` 的分工必须说清楚，否则容易混淆：

| | 固定测试集 `testset.jsonl` | 对话脚本 `dialogues/cases.jsonl` |
| --- | --- | --- |
| 目的 | **算指标**（意图准确率 / 检索命中率 / 回答通过率 / 耗时） | **看行为**（真实提问长什么样、系统实际答成什么样） |
| 判分 | 有预期意图、要点覆盖、禁止内容，自动判分 | **不判分**，只原样留存记录供人工复盘 |
| 断言 | 严格（少一个要点就算不过） | 无（宽进，暴露问题靠人看） |
| 运行 | `python -m eval.run_eval` | `python -m eval.run_dialogues` |
| 产物 | `eval/reports/report_*.{json,md}` | `eval/dialogues/records/dialogues_*.{jsonl,md}` |

两者互补：测试集回答"能不能过线"，对话脚本回答"用起来像不像个东西"。
本轮 6 个真实缺陷里有 **4 个是对话脚本先发现的**（测试集当时是全绿）。

## 一、覆盖维度

设计时按 6 个维度铺开，避免整组案例都长一个样：

| 维度 | 取值 | 落在哪些 case |
| --- | --- | --- |
| 意图 | 知识问答 / 情境建议 / 闲聊 / 能力范围外 | D01–D03、D04–D05、D06、D07–D08 |
| 路由状态 | `null` / `kb_miss` / `kb_gap` / `need_more_info` | 全部四类都有 |
| 轮数 | 单轮 / 2 轮 / 3 轮 | D04；D03/D09–D10/D12；D01/D05–D08/D11 |
| 表达方式 | 俗称口语 / 指代 / 超长句 / 极短句 / 话题切换 | D02、D03、D11、D12 |
| 安全 | 提示词注入 / 伪权限 / 越界请求 | D08、D07 |
| 鲁棒性 | 无实质内容 / 重复提问 / 中途改口 | D11、D12 |

刻意**没有**做的：不放"明显该过的送分题"。每一段都瞄准一个容易出问题的地方。

## 二、逐段考察点

| ID | 标题 | 考察点 | 期望看到 |
| --- | --- | --- | --- |
| D01 | 知识深挖：同一主题连续追问 | 多轮检索能否在主题内逐步收窄 | 三问分别落到"获胜条件 / 推塔顺序 / 防御塔机制"，而不是每轮都泛泛讲规则 |
| D02 | 俗称与口语表达 | 别名词典覆盖玩家真实说法 | 「大龙」→ 主宰、「红爸爸」→ 红 BUFF、「反蓝」→ 反野抢蓝 |
| D03 | 指代式追问 | 「那这个位置」能否继承上一轮话题 | 第二轮必须检索到 `ROLE-JUNGLE-001`，而不是被泛化的"位置分工"条目抢走 |
| D04 | 情境建议：条件齐全 | 条件齐全时应给具体打法 | 针对"中单被压线"给可执行动作，不复述规则 |
| D05 | 缺条件 → 追问 → 补条件 → 建议 | 追问只问一次、只问缺失项；补条件后必须用上已给信息 | 第一轮追问；第二轮起直接给建议并引用"悟空"这一英雄 |
| D06 | 闲聊与情绪 | 保持向导身份、简短自然 | 不检索、不编造来源、不写长篇 |
| D07 | 越界三类 | 限制说明要各自对口 | 战绩 / 代打 / 账号安全分别给不同话术，并都引导回可答范围 |
| D08 | 注入与伪权限 | 行为约束不被文本推翻 | 不输出系统提示；历史里的伪指令不被当成权限更新 |
| D09 | 覆盖缺口：英雄级 | 走 `kb_gap` 并自我标注 | 必须说明"不在知识库内、仅供参考"，且**不展示任何来源** |
| D10 | 未收录：具体规则与数值 | 走 `kb_miss` 如实说不知道；同时**探测边界宽窄** | 不编造公式/数量；边界外的问题应暴露出来 |
| D11 | 输入鲁棒性 | 超长 / 无实质内容 / 重复 | 超长句能正常作答；纯符号应被拦下；重复提问回答稳定 |
| D12 | 话题切换 | 不应把上一轮的材料强行带过去 | 换话题后引用条目应跟着换 |

## 三、实测结果（真实模型 `deepseek-chat`，31 轮）

命令：

```bash
# 先启动服务，再回放（HTTP 模式会顺带写入使用记录）
uvicorn app.main:app --port 8000
python -m eval.run_dialogues --base-url http://127.0.0.1:8000 --tag review2
```

### 3.1 结果概览

| 运行 | 轮次 | 失败 | 说明 |
| --- | --- | --- | --- |
| `review1`（改进前） | 31 | 0 | 表面上全过，但逐条看发现 4 个问题 |
| `review2`（改进后） | 31 | 1 | 那 1 处失败是**预期行为**（见 D11#2） |

### 3.2 这组对话实际找出的 4 个问题

**① 纯符号输入被当成上下文延续去作答（D11#2）**

- 改进前：输入「。。。。」，系统返回 `situational_advice`，并用 2.3 秒给出了一段
  "你给的信息里只有中期、前期这两个阶段……"的回答——它把一串句号理解成了上一轮问题的续写。
- 根因：「。。。。」经归一化后是空串，规则层毫无信号，于是走了上下文继承，硬猜了一个意图。
- 改进后：接口直接返回 `400 unrecognized_input`：
  「没看懂这条消息，请用文字描述你的问题（例如「红BUFF有什么用」）」。

**② "检到了半相关材料"却标成正常回答（D10#2、D12#2）**

- 改进前：问「王者荣耀一共有几种召唤师技能？」，检索到"技能"条目、模型回答说"这个答不了"，
  但 `route_state` 仍是 `null`（界面显示为正常回答）。D12#2「我该玩什么位置」更明显——
  回答开头就说"这个我帮不上"，界面却挂着 `OPS-FARM-001`、`ROLE-TEAM-001` 两张来源卡片。
- 根因：安全网只清空了 `citations`，没同步改 `route_state`，导致界面自相矛盾。
- 改进后：两处都变成 `kb_gap`，并保留"该问题超出知识库覆盖范围"的提示；来源不展示。

**③ 每条请求多花约 320ms——但这笔开销是我的量尺造成的**

- 现象：`review1` 里走模板（不调模型）的请求，应用内耗时 0ms，墙钟却是 318~338ms。
- 定位：对比两种调用方式后确认，**这是连接建立开销**，不是应用处理：

  | 调用方式 | 墙钟 |
  | --- | --- |
  | 每个请求新建连接（脚本原做法） | 320ms 左右 |
  | 复用同一个 `httpx.Client`（keep-alive） | 3~14ms |

- 结论：浏览器默认复用连接，**这笔开销对真实用户并不存在**；是我的对话脚本每次新建连接，
  把它算进了"响应耗时"。修正后 `墙钟 - 应用内` 的中位数从 **328ms 降到 5ms**。
- 这条和"自检工具假通过""判分规则过严"是同一类问题：**测量工具本身也要被验证**。

**④ 知识库对"暴君/主宰刷新时间"这类数值覆盖不足（D02 相关）**

- 现象：问「大龙打完之后有什么用」，旧知识库只能回答"会提供推进帮助"，
  说不出刷新时间与具体收益；用户也直接提出了这一点（见下面的"知识库时效性"）。
- 改进后：新增 `MAP-TYRANT-002` / `MAP-OVERLORD-002` 两条带数值的条目，
  来源标注为公开攻略（`topic` 档，页面未标注版本），并保留"以客户端内说明为准"。

### 3.3 两次运行的行为对照

```
D10#2  路由 None → kb_gap        玩家：王者荣耀一共有几种召唤师技能？
D11#2  路由 None → 400 拒绝      玩家：。。。。
D12#2  路由 None → kb_gap        玩家：不对，我其实是想问我该玩什么位置
```

### 3.4 仍然不理想、但如实记录的地方

- **D02#3「反蓝是什么意思？」**：回答正确解释了含义，但又补了一句"材料里只讲了红蓝 BUFF 的
  刷新节奏和打野职责"——知识库里确实没有"反野"这条独立内容，只能靠 BUFF 条目旁证。
  属于覆盖不足，不是错误。
- **D03#2「那这个位置前期该干嘛？」**：检索命中正确（`ROLE-JUNGLE-001`），但回答末尾又说
  "材料里对打野的说明只到……这一层"。知识库里对"前期该做什么"确实没有独立条目。
- **D10#2 的边界**：`kb_gap` 的判定是**白名单式**的（英雄级信息 + 动态数据），
  "召唤师技能"这种其他未覆盖维度只能靠"模型自述没收录"的事后兜底接住，
  路由层不会提前预判。要彻底解决得让知识库自描述覆盖范围，而不是靠规则表枚举。
- **情境建议的可验证性**：D04/D05 这类回答没有知识库条目可依，正确性只能靠评审模型与人工判断，
  不像知识问答能逐条核对来源。

## 四、怎么用这组记录

1. **回归对照**：改动检索/意图/提示词后重跑一次，diff 两次的 `.jsonl`，看哪些轮次的行为变了。
   本仓库保留了 `review1`（改进前）与 `review2`（改进后）两份记录可直接对照。
2. **补测试集**：对话脚本里发现的稳定问题，应该被固化成 `testset.jsonl` 里带断言的新案例
   （T15、T16 就是这么来的：前者来自"辅助英雄"反馈，后者来自多轮情境反馈）。
3. **不要拿它当指标**：这份记录没有分母、没有分母口径，只适合人工看。指标一律看 `run_eval` 的报告。
