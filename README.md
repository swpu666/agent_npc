# 训练向导「小玖」· 王者荣耀问答 Agent（最小可用 Demo）

面向玩家的游戏问答 Agent：**网页提问 → 意图识别 → 按需检索本地知识库 → 生成回答 → 网页展示结果与来源**，
并附带一套可重复运行的离线评测。设计说明见 [DESIGN.md](DESIGN.md)。

- 游戏：王者荣耀（原创向导 NPC「小玖」，不复刻官方角色）
- 技术栈：Python 3.11+ / FastAPI + 原生 HTML/CSS/JS
- 模型：任意 OpenAI 兼容接口（DeepSeek / 通义千问 / GPT 等），密钥只留在后端
- 返回方式：非流式 JSON，响应中带意图、引用来源与分环节耗时

## 二、快速开始

### 1. 安装依赖

```bash
python -m venv .venv
.venv\Scripts\activate            # Windows
# source .venv/bin/activate       # macOS / Linux
pip install -r requirements.txt
```

### 2. 配置模型

```bash
copy .env.example .env            # Windows
# cp .env.example .env            # macOS / Linux
```

编辑 `.env`，至少填好这三项（示例为 DeepSeek，换成任意 OpenAI 兼容服务都可以）：

```ini
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_API_KEY=sk-你的密钥
LLM_MODEL=deepseek-chat
```

`.env` 已被 `.gitignore` 忽略，不会进入仓库；前端页面与静态资源中不含任何密钥。

### 3. 启动服务

```bash
python -m app.tools.kb_lint        # 可选：知识库自检（零依赖）
uvicorn app.main:app --port 8000
```

浏览器打开 <http://127.0.0.1:8000/>。页面支持连续追问、清空对话、等待状态、失败重发，
知识类回答下方会展示实际使用的来源（标题 / 链接 / 采集日期 / 适用版本 / 相关度）。

右上角四个入口：**设计文档**（`GET /design`，本项目的设计亮点展示页）、
**玩家画像**（本会话的提问画像 + 跨会话的知识缺口，可一键清除）、
**评测报告**（`GET /report`，网页里直接逐条抽查最近一次评测）、
**使用记录**（最近 60 条，**只显示自己这个会话的**）。

### 4. 跑离线评测

```bash
python -m eval.run_eval                       # 默认：Agent 核心链路 + 测试集 16 例 + LLM 评审
python -m eval.run_eval --mode http           # 改为通过 HTTP 调用 /api/chat，验证真实接口链路
python -m eval.run_eval --no-judge            # 只跑规则断言，不消耗评审模型额度
python -m eval.run_eval --only T06,T09,T13    # 只跑指定案例
```

报告写入 `eval/reports/report_<tag>_<时间戳>.{json,md,html}` 三份：
- `.json` 机器可读（供二次分析）；
- `.md` 便于阅读与提交；
- `.html` **自包含单文件**（内联 CSS/JS，可离线双击打开，也可通过网页 `GET /report` 直接查看）。

HTML 报告带「只看未通过」筛选，并把实际回答、评审给出的原文证据、判决理由并排呈现，专供逐条抽查。

### 5. 跑多样化对话回放（看行为，不判分）

```bash
# 需要先启动服务；HTTP 模式会顺带把每轮写入使用记录
uvicorn app.main:app --port 8000
python -m eval.run_dialogues --base-url http://127.0.0.1:8000 --tag review
python -m eval.run_dialogues --only D05,D09 --mode core      # 只跑指定对话 / 走核心链路
```

14 段对话、40 轮的逐轮记录会写进 `eval/dialogues/records/dialogues_<tag>_<时间戳>.{jsonl,md}`。
**case 设计说明与实测结论见 [`eval/dialogues/README.md`](eval/dialogues/README.md)。**

这一套和 `run_eval` 的分工必须分清，否则会得出错误结论：

| | `run_eval`（固定测试集） | `run_dialogues`（对话脚本） |
| --- | --- | --- |
| 目的 | **算指标**：意图准确率 / 检索命中率 / 回答通过率 / 耗时 | **看行为**：真实提问长什么样、系统实际答成什么样 |
| 判分 | 有预期意图与要点断言，自动判分 | **不判分**，只留存记录供人工复盘 |
| 结论强度 | 能说"过线了" | 只能说"用起来像/不像个东西" |

两者互补：本仓库第 7 轮里，对话脚本首次运行就找出 4 个测试集**完全没覆盖**的问题
（当时测试集全绿）。**能过线的系统不等于好用的系统。**

仓库中已保留的报告（可复核）：

| 文件 | 说明 |
| --- | --- |
| `report_final1_*.{json,md,html}`、`report_final2_*.{json,md,html}` | 真实模型下的两次最终评测（18 例），各项质量指标均为 100% |
| `report_baseline_*.{json,md}` | 接入真实模型后的第 1 次全量运行，回答通过率 92.86%（T06 未通过） |
| `report_judge_rule_issue_*.{json,md}` | 暴露"判分规则过严导致 T05 假失败"的那次运行 |
| `report_smoke_*.{json,md}` | Mock 模式的链路验证结果，**不作为质量结论** |

问题定位与修正过程记录在设计文档 [DESIGN.md](DESIGN.md) 的 §4.5 与 §6。

## 三、Mock 模式（链路验证专用）

没有模型密钥时，可以用 Mock 模式先验证页面与接口是否连通：

```bash
# Windows PowerShell
$env:MOCK_LLM=1; uvicorn app.main:app --port 8000
$env:MOCK_LLM=1; python -m eval.run_eval --tag smoke --no-judge
```

Mock 模式**不会调用任何真实模型**，会在三处显著标识：页面顶部 `MOCK 模式` 徽标、
接口响应 `mock: true`、评测报告文件名前缀 `smoke` 与正文声明。
**Mock 结果只用于验证链路连通，不能替代真实模型调用及其质量评测。**

## 四、接口

### `POST /api/chat`

```json
{
  "message": "红BUFF多久刷新一次？",
  "session_id": "s-abc123",
  "history": [
    { "role": "user", "content": "打野的职责是什么？" },
    { "role": "assistant", "content": "打野负责……" }
  ]
}
```

`session_id` 可选：带上它，服务端会按会话累计画像并在后续回答中注入（≥3 轮才注入）；
不带则完全不启用记忆。前端在浏览器 localStorage 里自动生成并复用。

响应（节选）：

```json
{
  "request_id": "r-20260922-0001",
  "answer": "……",
  "intent": "knowledge_qa",
  "route_state": null,
  "citations": [
    { "id": "MAP-BUFF-003", "title": "红 BUFF 与蓝 BUFF 的刷新节奏",
      "url": "https://pvp.qq.com/…", "collected_at": "2026-09-22",
      "version": "数值随版本调整，以客户端内说明为准", "score": 8.2 }
  ],
  "timings": { "total_ms": 1357, "intent_ms": 0.4, "retrieval_ms": 0.3, "llm_ms": 1356 },
  "model": "deepseek-chat",
  "mock": false,
  "retryable": false,
  "memory": { "turns": 8, "topics": { "地图机制": 4 }, "profile_injected": true },
  "guard": { "injection_suspected": false, "notes": [] }
}
```

| 字段 | 说明 |
| --- | --- |
| `intent` | `knowledge_qa` / `situational_advice` / `chitchat` / `out_of_scope` |
| `route_state` | `need_more_info`（情境条件不足，已反问）、`kb_miss`（知识未收录，如实说不知道）、`kb_gap`（知识库覆盖不到，改用带标注的通用理解）、`unclear_input`（没看懂，拟人化引导）、`null` |
| `citations` | 只包含本次实际检索到的知识条目；无资料支持时为空数组，绝不伪造来源。`kb_gap` 强制为空 |
| `memory` | 会话画像摘要（提问次数、关注主题、本次是否注入了画像）；仅在请求带 `session_id` 时返回 |

**回答的依据强度是分层的**，页面会区分呈现：

| 依据强度 | `route_state` | 页面表现 |
| --- | --- | --- |
| 有知识库依据 | `null`（且 `citations` 非空） | 展示来源卡片（编号 / 标题 / 链接 / 采集日期 / 适用版本 / 相关度） |
| 只有通用理解 | `kb_gap` | 虚线提示条："超出知识库覆盖范围，以下为通用理解，仅供参考"。**不展示任何来源** |
| 完全没收录 | `kb_miss` | 说明未收录 + 给出可回答范围，无来源 |
| 没看懂 | `unclear_input` | 拟人化地承认没看懂并引导回可答范围（如"是暗号吗"），无来源 |

这样玩家能看出每条回答"依据有多强"，而不是把所有回答都当成同等可信。
| `timings` | 意图 / 检索 / 生成三段分别实测，单位毫秒 |

错误约定：

| 场景 | 状态码 | `error` | 前端行为 |
| --- | --- | --- | --- |
| 空输入 | 400 | `empty_input` | 明确提示 |
| 超过 1000 字 | 400 | `too_long` | 明确提示并保留输入 |
| 模型超时 | 504 | `timeout` | 展示「重新发送」 |
| 未配置密钥 / 模型 4xx | 502 | `config` / `http_4xx` | 展示原因，不重试 |
| 模型 5xx / 连接失败 | 502 | `http_5xx` / `connection` | 已按配置重试，仍失败可手动重发 |

另有四个辅助接口：

| 接口 | 用途 |
| --- | --- |
| `GET /api/health` | 服务状态、模型名、是否 Mock |
| `GET /api/kb/stats` | 知识库统计（条目数、主题与来源强度分布） |
| `GET /api/logs?limit=50&days=7&session_id=xxx` | **自己视角**：只返回该会话的记录；不带 `session_id` 时不返回任何记录。页面「使用记录」按钮即调用它 |
| `GET /api/logs/all?limit=100&days=7` | **管理视角**：返回所有会话的记录（供 `/allNpc/` 页面调用） |
| `GET /api/logs/stats?days=7&session_id=xxx` | 使用记录的聚合统计（按意图/路由状态/日期、独立 IP 数、错误数、平均耗时），可选择性按会话过滤 |
| `GET /api/reports` | 列出可查看的评测报告（标签、时间、模型、准确率、是否已生成 HTML） |
| `GET /api/reports/{name}/html` | 某次报告的 HTML；旧报告没有 .html 时用当前代码即时渲染 |
| `GET /api/memory/{session_id}` | 查看该会话的画像（系统记住了什么，玩家自己也能看） |
| `DELETE /api/memory/{session_id}` | 清除该会话的记忆 |
| `GET /api/knowledge-gaps` | 跨会话聚合"知识库没覆盖到"的问题，按被问次数排序 |

## 五、使用记录与隐私

每次问答都会写一条记录到 `logs/requests-YYYY-MM-DD.jsonl`，字段包括：
时间、`request_id`、**客户端 IP**、`X-Forwarded-For`、User-Agent、`session_id`、
**问题原文**、携带的历史轮数、意图、路由状态、**回答原文**、引用到的知识条目、分环节耗时、错误信息。

**自己视角 vs 管理视角是分开的**：
- 页面右上角「使用记录」按钮，只显示**自己这个会话**的记录（按 `session_id` 过滤），玩家自己也能看到系统记了什么；
- 查看**所有会话**的记录，走独立入口 <http://127.0.0.1:8000/allNpc/>（调用 `/api/logs/all`）。

```bash
curl "http://127.0.0.1:8000/api/logs?limit=20&session_id=你的会话ID"   # 只看自己
curl "http://127.0.0.1:8000/api/logs/all?limit=50"                     # 所有人（管理视角）
curl "http://127.0.0.1:8000/api/logs/stats?days=7"                     # 聚合统计
```

> **这不是安全边界**：`session_id` 可被前端伪造，`/api/logs/all` 与 `/allNpc/` 也没有鉴权，
> 知道 URL 的人就能看到所有记录。它只是产品层面的"默认只看自己"，真正的隔离需要登录与鉴权。

**隐私须知（重要，请先读完再用）**：

| 项 | 说明 |
| --- | --- |
| 记录内容 | **包含客户端 IP 与完整对话内容，属于个人信息** |
| 用途限制 | `X-Forwarded-For` **可被客户端伪造**，因此这些记录只用于本地调试与效果复盘，**不作为任何安全判断依据** |
| 仓库安全 | `logs/` 已被 `.gitignore` 忽略，不会进入仓库 |
| 体积控制 | 单条消息/回答默认截断到 2000 字符（`LOG_MAX_CHARS`） |
| 一键关闭 | `LOG_ENABLED=0` 后不再写入，`/api/logs` 会明确返回"已关闭" |
| **上线前还差什么** | IP 脱敏（截断或哈希）、向用户告知并取得同意、设置保留期与过期清理、限制访问权限。**当前实现只做到"仅本地、可关闭、不提交仓库"这三条，距离合规上线还差上述工作** |

**长期记忆同样涉及隐私**：会话画像文件（`app/data/memory/*.json`）包含玩家问过的**原始问题文本**。
它只统计"问了什么"（提问类型、关注主题、提到过的位置/英雄），**不推断"喜欢玩什么"**；
按会话隔离、不足 3 轮不注入、可随时通过「玩家画像」抽屉或 `DELETE /api/memory/{id}` 清除。
与使用记录一样，`app/data/memory/` 已被 `.gitignore` 忽略、可经 `MEMORY_ENABLED=0` 关闭。

知识未命中 / 需补充条件 / 没听懂）；调用模型的案例中，**等待时间的 99.9% 花在模型生成上**，

> 数字该怎么读：18 例全通过只说明**在当前测试集范围内**行为符合预期，不代表泛化能力已验证——
> 测试集由我自己编写，存在"测自己会的东西"的固有偏差。真实价值在开发过程中定位并修正的
> **8 轮共 36 项缺陷**，每一项都有可复核的失败证据，见设计文档 §4.6 与 §6。
> 其中 7 项是"检查本身不可靠"（判分规则过严、自检工具假通过、自己写的兜底误伤正常回答、
> 评测脚本把连接开销算进耗时），这类问题往往比被测对象的缺陷更难发现。
>
> 另外 14 段对话回放（`eval/dialogues/`）是**另一套独立的检验手段**：它不判分、只留存行为记录。

### 关于"知识库是不是不够新"

**在"具体数值"上确实不够新，在"机制"上够用。** 这一条值得正面回答，而不是含糊过去。

最初 31 条知识刻意**只写机制、不写数值**，把数值一律推给"以客户端内说明为准"。
理由是数值随版本变化、写进静态库必然过期——这个理由成立，但**执行得太极端**：
玩家问"暴君多久刷新"只能得到"会在一段时间后刷新"，几乎没有信息量。

现在的折中做法（新增 `MAP-TYRANT-002` / `MAP-OVERLORD-002`）：

| 做法 | 说明 |
| --- | --- |
| 补齐机制性数值 | 写明首刷时间、再刷间隔、击杀收益 |
| 标注不确定性 | `version` 写明"来源页面未标注版本，采集于 2026-09-22"，`confidence: medium` |
| 如实标来源强度 | 这两条是 `topic` 档：数值有来源，但**该页面没有版本标注**，也未涵盖 10 分钟后的进阶形态 |
| 回答层保留提示 | 回答中仍会提示"以客户端内说明为准" |

**仍然没解决的**：这些数值是否与当前版本一致，我无法在本地核实——需要对着客户端内的说明
或官方版本公告逐条比对。**没把握就不假装有把握**：宁可让回答带一句"以客户端内说明为准"，
也不要让玩家以为这是权威数值。

## 九、已知限制

- 非流式返回，首字感知延迟较高（用页面等待状态与阶段文案缓解）。
- 未引入向量检索，极端口语化表述可能漏召；漏召时如实回答「知识库未收录」。
- 会话不持久化，刷新页面即清空（题目未要求）。但**长期画像**会按 `session_id` 落盘，
  刷新页面仍能接续（`session_id` 存在 localStorage 里）。
- **长期记忆是"统计推断"，不是事实**：只记录"问了什么"，不推断"喜欢玩什么"；
  没有账号体系，`session_id` 隔离**不是**真正的用户级隔离。画像含原始问题文本，
  需注意隐私（可一键清除、可 `MEMORY_ENABLED=0` 关闭）。
- 数值类知识（如 BUFF 刷新间隔）随版本调整，知识库只标注版本范围，回答中会提示以客户端内说明为准。
- **来源强度不一致**：10 条是"直接来源"（页面写明），23 条只能算"主题来源"（页面覆盖该主题但非逐句对应）。
  也就是说**并非每条知识都有官方逐句出处**，这一点写在字段里、也显示在页面标签上，没有用统一措辞掩盖。
  想彻底解决需要把知识库收敛到"官方页面写明了什么就只收什么"，代价是知识量会明显变小。
- **数值可能已过期**：暴君/主宰的刷新时间与收益来自公开攻略页（未标注版本），
  **我无法在本地核实它们与当前版本是否一致**，需要对着客户端内说明逐条比对。
  回答中会保留"以客户端内说明为准"的提示，但这不能替代真正的版本核对。
- **使用记录含个人信息**：`logs/` 里有客户端 IP 与完整对话内容，当前只做到"仅本地、可关闭、不提交仓库"，
  **不满足合规上线要求**（还缺 IP 脱敏、用户告知与同意、保留期与访问控制），细节见「五、使用记录与隐私」。
- **`kb_gap` 的判定是白名单式**的（英雄级信息 + 动态数据两类）。像"召唤师技能有几种"这种
  其他未覆盖维度，路由层不会提前预判，只能靠"模型自述没收录"的事后兜底接住。
  彻底解决需要让知识库自描述覆盖范围，而不是靠规则表枚举。
- **知识库没有「英雄」维度**：只有通用规则，没有具体英雄、英雄推荐、使用率/强度排行。
  这类问题走 `kb_gap` 路由——由模型用自身通用理解回答，并**明确标注"不在知识库内、仅供参考"、不展示任何来源**。
  代价是这批回答无法逐条核对来源，正确性只能靠 LLM 评审与人工抽查，**可验证性弱于知识问答**。
  彻底解法是补一个可检索的英雄与策略知识库（"使用率排行"这类动态数据不适合进静态库，仍应如实说没有）。
